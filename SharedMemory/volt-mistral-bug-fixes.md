2026-07-04: fixed 4/5 bugs from `BUG_REPORT_OOP_ALLOCATION.md` (AI-generated report, all 5 repro'd before fixing). All uncommitted on branch Feat/Shared-Register-Stack along with the Phase 1-6 perf work.

- **VOLT-004** (S0032 false circular def on `next : ListNode`): `TypeCollector#resolve_field_type` force-resolved every declared nominal → cycle guard misfired. Now only force-resolves `StructDecl` fields (by-value embedding needs layout; class fields are pointer-sized refs, deferring is safe since `Type.from_annotation` only needs the eagerly-created NominalType).
- **VOLT-002** (`nil` unparseable): dead `when .nil?` branch — the Crystal enum/Object#nil? shadowing trap (see [[crystal-gc-atomic-value-payload]]). Fixed in ParseExpression nud + can_start_expr, Lexer division_allowed?, Type#to_s. Downstream (NilLit → TypeChecker/FunctionEmiter) already existed.
- **VOLT-001** (`next` reserved): Mistral's report was WRONG — user overrode (2026-07-04): `next` must stay reserved, matching Ruby/Crystal (`next : ListNode` as a field name is correctly rejected there too). Initially removed the keyword, then reverted and instead *implemented* `next`/`break` as real loop-continue/break, since neither was actually wired to the compiler before (break parsed to `BreakExpr` but hit `S0023 not supported` in TypeChecker — first-class feature gap, not a false alarm). Added: `NextExpr` AST node (mirrors `BreakExpr`, optional value); `TypeChecker` `@loop_depth` counter + `break_outside_loop`/`next_outside_loop` (S0052/S0053) diagnostics; `FunctionEmiter::LoopCtx` (continue_target/result_reg/break_jumps) pushed/popped around `compile_while`'s body — `next` jumps straight to the condition recheck, `break`/`break value` jumps past the loop (value written into a pre-allocated result register, Ruby/Crystal `break value` semantics). No RAII interaction needed: `enter_scope`/`exit_scope` only wrap whole function bodies in this compiler, never loop bodies, so jumping out mid-body skips no `DROP_SCOPE`. `until`/`while` share one AST node (`until` desugars to negated `WhileExpr` at parse time) so both got the fix for free.

**Follow-up same day** — user added `Samples/Tests/01.q.Prec.vl` exercising postfix modifiers + if-as-expression + ternary, surfacing 3 more real gaps, all fixed:
- **Postfix `break`/`next`/`return` with NO value** (`break if cond`): `expr_if_on_same_line` ate the modifier keyword itself as a value-expression `nud` (`if cond ... end`), swallowing the rest of the enclosing body hunting for `end`. Fixed: it now returns `nil` (no value) when `@current` is itself `if`/`unless`/`while`/`until`, letting the statement-level `parse_expr` loop apply it as a modifier via `led` instead.
- **Postfix `while`/`until` never wired at all** (only `if`/`unless` were, despite `Prec.cr`'s own comment listing all four): added `.while?`/`.until?` to `led_prec` (→ `Prec::Modifier`) and `led` (builds `IfExpr`, `until` negates — same as `unless`). Deliberately single-shot (matches `if`/`unless`), NOT a real Ruby postfix *loop* — indistinguishable for `break`/`next`/`return` (control never returns to re-check), and no caller needs the looping form yet.
- **`if`-as-expression had no static type** (`res = if x > 10 ... else ... end; res + 1` → spurious `S0012` numeric-operand error): `compile_if` already correctly merges branch values into one register at runtime, but `TypeChecker#infer_if` hardcoded `Type::NIL` regardless of branches. Fixed: unify `then`/`elsif`/`else` branch types (`unify_branch_type`, permissive — falls back to `Unknown` on disagreement, same stance as `type_compatible?` elsewhere); a missing `else` implicitly unifies with `Nil` (condition-false-fallthrough).
- **Ternary `cond ? a : b`**: didn't exist (`?` was `?.` safe-nav only). Desugared straight to `IfExpr` at parse time in `led`'s `.question?` arm (branch on `@current.kind.dot?` to pick safe-nav vs ternary) — reuses the just-fixed `infer_if`/`compile_if` for free instead of a parallel `TernaryExpr`. New `Prec::Ternary` (between `Assignment` and `Or`, renumbered the whole enum — all other refs are symbolic, safe). Both branches parsed at `Ternary.value - 1` (= `Assignment`): lets nested ternary chain right-associatively (`a?b:c?d:e`) and left-nest without parens, while still stopping at `:` rather than misreading it as the typed-local-decl colon (`x : Type = v`). Known follow-on gap, not fixed (rare, no caller): assignment inside a ternary branch without parens (`c ? x = 1 : y = 2`) doesn't parse — matches typical C practice of requiring parens there too.
- Also found, NOT fixed (pre-existing, unrelated to any of the above): a bare local var followed by safe-nav (`b?.v` where `b` is not otherwise `?`-suffixed) mis-lexes as one identifier token `"b?"` — the lexer's "identifier may end in `?`/`!`" rule (for predicate-style method names) doesn't distinguish "trailing `?` is part of this name" from "trailing `?` is the safe-nav operator on a separate name". `Box.new(...).v` chains and `?.` after a method call/parenthesized expr are unaffected — only a bare `ident?.` is broken. Real fix needs lookahead in the lexer or a parser-side split (mirrors the exact same class of bug as VOLT-003's `ListNode?` gluing, fixed on the type-annotation side already).
- New sample `01.q.Prec.vl` needs a `Spec/Samples/Data.cr` entry (`"PASS\n"*10`) — easy to forget since `krystal -s` errors with a cryptic `KeyError` backtrace instead of a normal spec failure when a sample has no registered expected output.
- **VOLT-003** (`Type?`): parser already produced NilableType but lexer glues `?` into the ident (`ListNode?` = one Ident token) → ParseType now splits trailing `?` off the name. `Type.from_annotation` erases `T?` → `T` for Object-kind only (structs/primitives stay unsupported — unboxed reps can't hold nil). Semantics = Java-style implicit nullable class refs: `type_compatible?` accepts Nil→Object, `==`/`!=` vs nil always OK (runtime compares tags; HeapObject fields already nil-init'd). `A | Nil` union syntax still unsupported (P0001) — `T?` is the supported spelling.
- **VOLT-005** (Object/Any base type): NOT fixed — deliberate 0.1.0 design gap needing a real language decision (vtable/root-type semantics); abstract-class workaround exists.

Validation: 238/238 specs (incl. the 2 pre-existing failures fixed by the GC root cause, and the new `01.q.Prec.vl`), bench --check ok, perf flat (fib ~1.16-1.3s, primes ~0.07-0.08s throughout).
